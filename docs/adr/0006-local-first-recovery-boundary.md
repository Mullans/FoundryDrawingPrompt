# Local-first recovery boundary and precedence

Ongoing drawing recovery is owned by a Recovery generation in the player's IndexedDB, preserving foreground pixels first and attaching coherent bounded undo/redo history when storage permits. History uses immutable 128×128 RGBA tile versions and pixel installation, not command replay or rolling full-canvas checkpoints. Each changed tile retains one directional reference: applied actions point to the Undo target, undone actions point to the Redo target, and traversal swaps that reference with the sparse current tile map. The in-memory history retains at most 25 actions and may evict older actions sooner under its pixel or metadata budgets. Neither that history nor its persistence records are sent to the GM.

Recovery generations reference stable, writer-scoped tile-version IDs in a shared IndexedDB tile store. Saves write only missing versions in bounded batches, publish artwork after its required versions exist, and attach history only after all additional versions exist. A newer edit supersedes optional history work without invalidating artwork already published for that generation. Failed or superseded staging records release their pins and collect orphan tiles. This keeps unchanged pixels shared across consecutive generations and lets artwork survive interrupted optional-history work.

On resume, a retained in-memory session wins, followed by the newest valid local generation. Local artwork remains recoverable when its optional history attachment is absent or corrupt. Only when the local Recovery copy is missing may recovery use the newest available GM-held capture that belongs to the same Assignment and contains usable full-quality Submission image data; that fallback is restored as flat pixels with empty history. Quick GM previews and Saved previews are never eligible. This boundary avoids continuous transfer and retention of full-quality work while preserving same-browser recovery, accepting that clearing browser storage or changing devices can lose work that was never fully submitted or captured before the Prompt became Closed.

Alternative rejected: periodic full-quality GM checkpoints. They would improve cross-device and unavailable-player recovery, but add continual bandwidth, retention, acknowledgement, and revision-reconciliation costs; they also create competing authoritative copies.

Alternative rejected: recover from quick GM previews or Saved previews. They are reduced or artwork-only review artifacts and cannot preserve editable history, so treating them as recovery would silently degrade or misrepresent player work.
